# ADR-009: Multi-Stage Distroless Containerization with Custom JRE & Build Strategies

## Status
**ACCEPTED**

## Date
2026-09-07

## Context
SmartPay operates a multi-service financial logistics platform comprising 8 executable Spring Boot microservices and 2 shared libraries. All services run on modern **Java 25** with Project Loom (Virtual Threads) and the Z Garbage Collector (ZGC).

Deploying these microservices to Kubernetes environments (KinD, Staging, Production) requires container images that satisfy strict security, performance, and operational constraints:
1. **Attack Surface Minimization**: Financial compliance demands zero package managers (`apt`, `apk`), zero interactive shells (`sh`, `bash`), and non-root execution (UID `10001`).
2. **Java 25 Runtime Availability**: As of early 2026, standard vendor-managed distroless images (such as Google's official `distroless/java`) only provide up to Java 21, lacking official Java 25 distroless runtime tags.
3. **Artifact Isolation**: Each microservice must produce its own self-contained executable fat JAR (`~60-90MB`) and distinct OCI container image, avoiding monolith sharing or class leakage.
4. **Local & CI Build Performance**: Developers and CI runners must be able to package and load 8 container images into KinD without downloading Maven dependencies repeatedly inside container build contexts.

## Evaluated Alternatives

### 1. Traditional OS Base Images (`eclipse-temurin:25-jre-noble` / Alpine)
* **Pros**: Readily available, easy to debug with interactive bash shell.
* **Cons**: Fails strict compliance. Contains full OS userland, package managers (`apt`), shells (`bash`), and unnecessary utilities that significantly expand the CVE attack surface and image size (`>300MB`).

### 2. Google Jib Maven Plugin (`jib-maven-plugin`)
* **Pros**: Fast daemonless builds, automatic layer separation (dependencies vs classes).
* **Cons**: Jib requires a pre-existing base image containing a full JRE. Because no official `distroless/java25` image exists from Google, Jib would require maintaining and publishing a custom external base image before building any service.

### 3. Spring Boot Cloud Native Buildpacks (`mvn spring-boot:build-image`)
* **Pros**: Zero Dockerfile management, standardized OCI metadata.
* **Cons**: Buildpack lifecycle downloads heavy builder images (`~1GB`). Paketo buildpack stacks often lag behind new OpenJDK releases (Java 25). Runtime user defaults to CNB UID `1000` rather than platform standard `10001`.

### 4. Multi-Stage Dockerfile with Custom `jlink` JRE & Distroless Base
* **Pros**:
  * Builds a minimal, stripped Java 25 JRE (`/opt/jre-25`) using `jlink`, stripping debug symbols and unneeded modules (`--strip-debug --compress=2`).
  * Deploys onto `gcr.io/distroless/cc-debian12:nonroot` containing only C runtime libraries (`glibc`).
  * Zero shell, zero package manager, strictly runs as UID `10001:10001`.
  * Total container image size is reduced to `~106MB` including JRE and fat JAR.
* **Cons**: Requires maintaining the Dockerfile definition and managing `jlink` module lists.

## Decision
Adopt **Alternative 4: Multi-Stage Distroless Containerization with Custom JRE**, augmented by a dual build strategy:

1. **Standalone Build (`docker/Dockerfile`)**:
   * Accepts `--build-arg MODULE_NAME=<service>`.
   * Compiles source code, runs `jlink`, and packages distroless image in an isolated container environment. Ideal for pull request validation and secure remote builds.
2. **Fast Prebuilt Strategy (`docker/Dockerfile.prebuilt`)**:
   * Reuses the pre-compiled fat JARs generated by host/CI Maven execution (`--build-arg JAR_FILE=<service>/target/*.jar`).
   * Cuts local KinD image build time from ~2 minutes to ~2 seconds per container by caching the `jlink` builder layer.
3. **Dedicated Executable JAR Packaging**:
   * Configure `spring-boot-maven-plugin:repackage` across all 8 executable microservices to produce distinct fat JARs while keeping `smartpay-proto` and `smartpay-common` as standard library JARs.
4. **KinD Local Cluster Automation**:
   * Automated via `scripts/ci/build-and-load-kind.sh`, which packages and imports all 8 container images into the local KinD cluster via `kind load docker-image`.

## Consequences
* **Positive**:
  * **Minimal Attack Surface**: Zero vulnerabilities reported by Trivy for OS userland; non-root execution (UID 10001).
  * **Zero Base Image Drift**: Exact Java 25 runtime consistency guaranteed across Dev, Staging, and Production.
  * **Rapid KinD Feedback**: Near-instant local container builds when iterating with pre-compiled JARs.
* **Negative**:
  * If a microservice introduces an exotic Java standard module not included in the `jlink` list, the module declaration in the Dockerfile must be updated.
